# B09 · aporte administrativo visible (admin.v1)

Este corte conecta M144 con un flujo manual para un turno: personal autorizado emite o revoca un enlace, el paciente aporta datos sin cuenta, y el personal revisa propuestas identificadas como **«aportado por el paciente»**. No incorpora valores a la ficha ni crea preguntas clínicas. El formulario no condiciona la atención.

## Uso y límites

- En el detalle del turno del calendario, **Emitir enlace** pide confirmar porque reemplazar revoca el anterior. El enlace y el QR se generan y muestran allí; el QR se codifica localmente en el navegador. El token solo se devuelve al emitir. Si la respuesta de emisión o revocación se pierde, no se puede recuperar el resultado desde M144. La interfaz conserva en memoria del módulo un bloqueo por turno aunque el modal se cierre y reabra; no permite otra emisión o revocación desde ese control y pide intervención. No guarda token, turno ni datos personales en web storage. Este bloqueo se pierde al recargar la página o abrir otra sesión: no constituye una garantía durable.
- El enlace usa `/aporte#token=…`. Un script retira el fragmento antes de hidratar el formulario. El intercambio crea una cookie propia `HttpOnly`, `SameSite=Strict`, `Secure` en producción y limitada a `/api/patient-intake`, con vencimiento devuelto por M144. El enlace compartido permite aportar datos, **no verifica identidad**.
- El navegador conserva respuestas y el identificador de operación solo en memoria. Antes de transmitir respuestas consulta el estado con un marcador opaco ligado a la sesión; el servidor coteja ese marcador con la cookie otra vez antes de cualquier RPC. Si otra pestaña sustituyó la cookie antes de esta comprobación, no se transmite el borrador. Si la sustituye en la carrera entre esa comprobación y el POST, el servidor rechaza el cuerpo antes de llamar a la base: nunca puede aceptarse para otro turno. Una vez intentado el envío, el contenido y la operación quedan congelados. `not_received` es provisional: habilita solamente volver a enviar **la misma operación y el mismo contenido**, porque el primer POST podría terminar después. Revocación, vencimiento o fallo de consulta quedan inciertos. Un plazo de 15 segundos cubre `fetch` y la lectura JSON; agotarlo no se interpreta como rechazo confirmado.
- `admin.v1` acepta datos personales, contacto y cobertura, omite vacíos y normaliza NFC. El límite canónico es 16 KiB. Nunca se envía el texto a analítica. La página marca el contenido sensible; PostHog del proyecto solo inicializa en la landing y Sentry descarta URL, cuerpos, breadcrumbs y replay. La página y las respuestas indican no almacenar en caché y no enviar referrer.
- Las acciones del personal derivan organización de la sesión activa y llaman las RPC autenticadas de M144. El `assert_access` de la base revalida `aal2`, factor y sesión vigentes, además de membresía y alcance del turno. El cliente público dedicado usa exclusivamente RPC service-only de M144 y no recibe cookies de staff.
- Las rutas públicas exigen `Origin` exacto y JSON para cada POST; el cuerpo se limita durante lectura de stream. En producción la ausencia del limitador distribuido bloquea el acceso público. Los fallos de credencial y sesión tienen respuesta genérica.

## Pruebas de este corte

- `pnpm typecheck`.
- `pnpm test:unit tests/unit/patient-intake-routes.test.ts tests/unit/patient-intake-http.test.ts tests/unit/patient-intake-admin-v1.test.ts tests/unit/patient-intake-recovery.test.ts`: ruta anónima, CSRF, límites, vínculo de sesión entre pestañas, validación administrativa, plazo del navegador y contención en memoria de acciones inciertas.
- `pnpm test:e2e tests/e2e/patient-intake.spec.ts`: navegador real con API sintética aislada, escritorio y móvil, teclado, fragmento retirado, respuesta perdida, `not_received` provisional con reintento idéntico, revocación incierta, recuperación del recibo y sustitución de cookie. Las pruebas de navegador no usan un backend M144 real.

Pendiente para la prueba integrada: recorrer **emisión → intercambio → presentación → revisión** contra una instancia Supabase/PostgreSQL sintética ya aislada y con M144 instalada, incluyendo revocación durante envío y negativa entre organizaciones. No se ejecutó contra producción ni se inició Docker local. El SQL M144 y sus carreras se verifican por separado; un navegador con respuestas simuladas no acredita el extremo de base de datos. La incorporación a ficha, con comparación de valores vigentes y conflictos, queda para otro paquete.

**Límite de publicación:** M144 no tiene operación idempotente ni consulta durable para la emisión. Tampoco un `revoke` confirmado ordena una emisión HTTP anterior que aún no adquirió el lock. El bloqueo de memoria de esta interfaz es una contención temporal, no una recuperación segura ante recarga, otro navegador o ejecución tardía. La idempotencia y el orden durable de emisión/revocación requieren el contrato de base siguiente (M147); este corte no se considera listo para entrega hasta integrarlo y probarlo.
